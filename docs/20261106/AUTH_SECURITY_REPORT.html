Security & access control

Who can get in, what they can touch, and what happens when they try more

PoWatch is a building where every door is locked unless it has a sign saying "public". Microsoft checks your ID at the entrance. You then wear a tamper-proof visitor badge (a cookie) that only opens your own drawer in the filing cabinet.

Signing in

PoWatch never sees your password. Microsoft does the checking and sends back a signed note. The server reads it, checks your organisation is on the guest list, and gives your browser a sealed badge. The browser can wear the badge but cannot open it.

  1. Start/auth/login/microsoft issues an OIDC challenge (authorization code with PKCE, scopes openid profile email).
  2. No open redirectsreturnUrl must start with / and must not start with //. Anything else becomes /.
  3. Tenant gateThe issuer's tenant id must exactly match an entry in AzureAd:AllowedTenants. A substring match is not enough.
  4. BadgeThe cookie is named __Host-PoWatch.Auth. It is HttpOnly, Secure-only and SameSite=Strict, and its key ring lives in Blob Storage so restarts do not log people out.
  5. XHR-friendlyAn API call without a badge gets 401 and a forbidden one gets 403, never an HTML redirect.

What happens on an unauthorised or bad request

  1. No badge401. The client shows the sign-in page.
  2. Too fast429, from a sliding window of 300 per minute in 6 segments. The limit is keyed by user id, or by IP address when anonymous.
  3. Not yoursLookups are made inside your own partition, so another user's session simply "does not exist" (404).
  4. MalformedThe FluentValidation shape check and domain time checks return 400 with readable reasons.
  5. Crash500 ProblemDetails with a trace id. The stack trace is hidden unless ExposeDebugDetailsInUi is on.

Protecting tokens, keys and secrets

Tokens

This is the BFF pattern: the Blazor client never sees an access token. Microsoft's tokens are saved inside the encrypted cookie on the server's side (SaveTokens = true).

Cookie keys

The Data Protection key ring is persisted to the dataprotection-keys blob, using managed identity when a service URI is set, under application name PoWatch.

Secrets

No secret is committed. Keys are blank in appsettings.json and come from Key Vault (Gemini--ApiKey) or App Service settings. Azure OpenAI prefers keyless Entra sign-in.

AI-specific protections

Captions and names are untrusted input written by a camera or a keyboard. They reach a model only as fenced <facts>, stripped of control and fence characters, capped at 300 and 80 characters at ingest, and with an explicit "never an instruction" rule. Gaps found, with proposed fixes

Nothing here is an open door, but a few locks could be tighter. Each item below is a proposal for you to approve; none of them has been changed.

Medium No CSP, frame-ancestors or HSTS on the main app. Only the shared-recap page sets a Content-Security-Policy. The SPA sets COOP/COEP but nothing stops it being framed (clickjacking), and there is no UseHsts(). App Service has httpsOnly: true and TLS 1.2 or higher, which covers transport, but not the browser-side pinning.
Proposed: in UsePoWatchResponseHeaders, add Content-Security-Policy: frame-ancestors 'none' (a narrow start, since a full policy for Blazor WASM needs 'wasm-unsafe-eval' and the model CDNs), and call app.UseHsts() outside Development.
