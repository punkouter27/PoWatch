System architecture & flow

How the pieces fit together

Think of a newsroom. Reporters in the field (your browser) phone in short notes. The front desk (the API) checks the caller's badge, the filing clerk (the ingest service) files each note once and updates the running totals, and the editors (stats and recap services) write the paper from those totals.

Sensing runs in the browser, and the server only ingests 10-second ticks and serves rollups. Four layers point inward: Domain ← Application ← Infrastructure / Api, with Shared holding DTOs and browser-safe logic.

C4 level 2 · Containers

Four boxes do the real work: the browser app, the web server, the filing cabinet, and (optionally) an AI writer.

  1. Browser appPages plus the C# parts that are safe to run in a browser (CentroidTracker, TickBatcher, VlmScheduler).
  2. WorkersHeavy models run off the main thread, using WebGPU when available and WASM otherwise.
  3. APIOne host serves the app files, the JSON API, the live hub and two timers (retention and digest).
  4. StorageTables hold the notes and totals, and blobs hold snapshot photos and the cookie-encryption key ring.

C4 level 3 · Inside the API

The server is a stack of layers. The front desk takes requests, service clerks do the work, and storage clerks talk to Azure. Each layer only calls the one below it.

The request assembly line (middleware)

Every request passes the same stations in the same order, like a security checkpoint. Order matters: the speed limit comes after the badge check, so it can count per person, not per building.

  1. Commit tagEvery response is stamped X-Commit, so a deploy can tell which build answered.
  2. Error netAny crash becomes a tidy "ProblemDetails" 500. The stack trace is shown only when debug details are on.
  3. HTTPSOutside Development, plain HTTP is redirected.
  4. Correlation idEach request gets an id that every log line carries.
  5. AuthenticationRead the badge (cookie, or the guest scheme in Dev/Test).
  6. User log scopeLogs carry the caller's partition id.
  7. AuthorizationDefault deny: anything not marked public needs a signed-in cookie.
  8. Rate limiter300 requests a minute per user on /api, /auth, /hubs and /s.
  9. Isolation headersCOOP/COEP make the page cross-origin isolated, so WASM models can use threads.
  10. EndpointsStatic files, then feature routes, then the SPA fallback. Unknown /api/* routes return 404.

Sequence · one batch of ticks

The browser sends a numbered envelope. The server checks it, files the contents, and updates the totals only if that envelope number has never been seen before, so resending never double-counts.

  1. Shape checkAt most 360 ticks and 2,000 events per batch. Event text is capped at 300 characters and names at 80.
  2. Time checkA tick more than 5 minutes outside its session is rejected, so old days cannot be rewritten.
  3. Raw firstRaw rows are keyed so a replay overwrites them rather than adding duplicates.
  4. ClaimOnly the first claim of a batchKey merges totals, with up to 32 merges in parallel.
  5. NotifyThe stats cache for that user is cleared, and only that user's tabs get the push.

Data model

Each user has their own drawer. Inside it are sessions, the 10-second notes from each session, events (someone came in, a caption, a sound), and pre-added totals. Share links live in a separate drawer, filed by link code, so a public reader can find one in a single lookup.
